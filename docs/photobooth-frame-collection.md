# 포토부스 프레임 50종 · 관리자 관리 · 빠른 반영

2026-09-23. 신규 50종 + 기존 6종을 `/admin/photobooth`의 동일한 프레임 목록에서 관리한다. 별도 DB 마이그레이션이나 초기 데이터 입력은 필요 없다. 배포하면 카탈로그가 표시된다.

## 디자인과 레퍼런스

새 PNG는 1200×1800, RGBA, 300 dpi, 기존 4×6인치 인화 캔버스용 오버레이다. 웹 자료에서는 디자인 계열과 모티프를 참고했으며 외부 이미지를 복사하거나 합성하지 않았다. 자체 SVG 원본에서 투명 PNG와 200×300 WebP 썸네일을 생성한다.

- 인생네컷 공식: https://lifefourcuts.com/ — 필름 프레임 소개 검색 결과 참고(본문 접근은 403).
- Cutiora: https://cutiora.com/tools/photobooth — 클래식·레이스·카페·생일·스크랩북 계열.
- 리본 생일 프레임: https://www.etsy.com/listing/1884123082/ribbon-photo-booth-template-overlay-for — 리본과 여백 사용.
- 필름 프레임: https://www.etsy.com/listing/764155148/filmstrip-photo-booth-template — 필름 퍼포레이션과 시네마 모티프.
- MyPhotobooth: https://www.myphotobooth.com/standard — 이벤트별 색과 텍스트를 바꾸는 포토스트립 카탈로그.

각 5종씩: 기본, 리본·레이스, 카페·디저트, 레트로, 생일파티, 팬클럽, 문구·스크랩, 꽃·계절, 별·드림, 취향·컬처.

모든 글자·바코드·번호는 가장자리에서 40px 안쪽에 둔다. DS-RX1 PR(4x6) 인화는 413×615(1/100인치) 페이지를 4×6으로 잘라 1200×1800 원본의 위아래 약 28px, 좌우 약 19px가 잘리기 때문이다(검사 스크립트가 SVG 글자 위치로 확인). 하단 제작 표기 줄은 잘림 영역에 걸려 제거했다.

사진 중앙을 투명하게 유지하고, 새 50종 모두 기존 행사 푸터 사각형(x=36~1164, y=1564~1764)을 완전히 비워 주인공 이름·해시태그·주최자·날짜를 보존한다. 현재 1컷 및 2×2 네컷 레이아웃 위에 적용하는 장식 프레임이며 사진 슬롯을 재배치하지 않는다. 특정 연예인 사진·이름·공식 로고는 들어 있지 않다.

## 관리

- `/admin/photobooth`: 업로드 추가, 활성/비활성, 순서, 삭제. 검색으로 56종과 업로드 항목을 찾는다.
- `/booth`의 레트로·클래식 테마 모두: `FramePicker`(`variant="retro" | "classic"`)로 분류별 선택과 200×300 썸네일, 4열 고정 높이(15rem) 스크롤 영역. 레트로는 입체 선택 버튼, 클래식은 둥근 카드 모양이다. 56종이어도 완성하기·다시 찍기 버튼은 1280×720(150% 배율) 화면 안에 있다 — 클래식 편집 화면의 오른쪽 열은 넘치면 자체 스크롤하고 버튼 줄은 열 바닥에 붙는다.
- 관리자 목록도 썸네일로 표시한다(원본 PNG는 합성할 때만 받는다).
- 설정을 받기 전과 첫 조회가 실패했을 때는 기본 56종을 먼저 보여 준다.
- 기본 프레임의 식별자는 고정 UUID다. 사용자 변경은 기존 `photobooth_assets` 테이블에 해당 UUID의 override 행으로 저장한다.
- 기본 프레임 삭제는 `image_url = 'catalog:deleted'`와 `is_active = false`로 남긴다. 이 삭제 표식은 관리자·공개 목록에서 모두 제외한다. 파일은 보존되지만 앱에서 자동 복원되지 않는다.
- 사용자 업로드 항목은 기존 삭제 방식을 유지한다. 카탈로그 행을 DB에서 직접 지우면 기본값으로 되돌아오므로 운영 변경은 관리자 API를 사용한다.
- 기본 프레임은 행사에 묶지 않는다(PATCH에서 `event_id` 무시). `event_id` 외래키가 `ON DELETE CASCADE`라 행사를 지우면 설정 행이 함께 지워지고, 숨겨 둔 기본 프레임이 다시 보이게 되기 때문이다.
- 비공개/종료 이벤트의 override까지 읽은 뒤 카탈로그를 합치고 노출 조건을 적용한다. 공개 응답에는 활성 상시/현재 행사 소재만 포함한다.

## 동기화

화면이 보이는 동안 1초마다 설정 API를 읽는다. 응답에 ETag(본문 sha1)를 붙이고 `Cache-Control: no-cache`로 매번 확인하게 해, 바뀐 게 없으면 본문 없이 304를 받는다(응답 약 17KB × 하루 86,400회 ≈ 부스당 1.4GB → 거의 0). 요청 횟수와 DB 조회는 그대로 1초에 1번이다. 통상 반영 시간은 0~1초 + 서버·네트워크 응답 시간이다. 서버 push 방식은 아니다. 포커스 복귀와 네트워크 복구에도 즉시 조회한다.

동시 요청을 방지하며 8초 타임아웃 후 재시도한다. 응답이 동일하면 상태를 갱신하지 않아 매초 사진을 재합성하지 않는다. 오류/오프라인 중에는 현재 목록을 유지한다(오프라인 재시작용 영구 캐시는 추가하지 않았다). 편집·결과 화면에서는 손님이 고른 프레임을 유지한다(관리자가 그 사이 숨기거나 지워도 합성·저장·인쇄 결과가 바뀌지 않음). 그 밖의 단계에서 선택 프레임이 사라지면 프레임 없음이 된다. 다음 손님은 처음으로 돌아갈 때 선택이 초기화되어 현재 목록 기준으로 시작한다. 이미 출력한 인화물에는 소급 적용되지 않는다.

새 프레임 이미지·API·두 부스 화면을 함께 배포해야 한다. 아직 Git에 추가되지 않은 새 파일(`src/components/photobooth/`, `src/hooks/useLiveBoothConfig.ts`, `src/lib/photobooth/frame-catalog.*`, `src/app/admin/components/AdminTabs.tsx`, `public/assets/photobooth/`, `public/booth/`)도 함께 커밋해야 빌드된다. `design-review/`와 `artifacts/`는 Git에서 제외되며 배포에 필요 없다. 기존 배포본은 종전 코드로 동작하며 이 작업 자체로 운영 사이트를 배포하지는 않는다.

## 파일과 검증

- `src/lib/photobooth/frame-catalog.json`: 새 50종 정의
- `src/lib/photobooth/frame-catalog.ts`: 기본 목록과 override 병합
- `public/assets/photobooth/frames/`: SVG·PNG·WebP
- `/booth/frames-preview.html`: 50종 검토 갤러리
- `/assets/photobooth/frame-collection-preview.jpg`: 전체 시트
- `node scripts/generate-photobooth-frame-collection.mjs`: 에셋 재생성
- `node scripts/verify-photobooth-frames.mjs`: 50종 규격·투명 영역, 관리자 권한, 숨김·삭제 유지, 행사 범위, 폴링 중복 방지·오프라인 보존 검증. DB와 네트워크는 모형으로 검사하여 운영 데이터는 변경하지 않는다.

검증 결과(통합 후 재실행): 프레임 회귀 검사 5개(인쇄 잘림 안전 영역, 304 재검증 포함), 기존 인화 검사, TypeScript, 변경한 신규 모듈/API의 ESLint, 프로덕션 빌드 통과. 로컬 실제 공개 API에서 총 56종(신규 50종)을 확인했고, 비로그인 관리자 API는 403을 반환했다. 실물 카메라·프린터 및 운영 배포는 이번 검증 범위에 포함하지 않았다.

브라우저 검사(1280×720, 150%, 레트로·클래식 모두): 홈→이용권→촬영→편집→프레임 선택→결과→저장 QR 화면에서 가로 넘침·화면 밖 버튼·오류 없음. 설정 응답을 가로채 숨김·순서 변경 0.2~0.7초 반영, 편집 중 선택 프레임 삭제 시 선택·합성 유지, 500·오프라인 동안 목록 유지 후 복구 반영을 확인했다. 관리자 화면은 조회만 실제로 하고 변경 요청은 가로채 요청 내용만 확인했다. 설정·이용권 API를 모형으로 대체했고 인쇄/완료 동작은 실행하지 않았다.
